Persistencia del broker

El broker declara un nombre de nodo estable (rabbit@pedidos360-rabbitmq) y un vhost explicito. Sin un hostname fijo, RabbitMQ deriva el directorio de datos del ID del contenedor; al recrearlo con docker compose down + up ese directorio cambiaba y la topologia y los mensajes se perdian pese a tener montado el volumen rabbitmq_data. Con el nombre fijo, la topologia y los mensajes sobreviven a la recreacion.

Garantia transaccional

COMMIT → evento. ROLLBACK → cero eventos. Verificado con transaccion externa sobre H2 en ambos servicios: un rollback no deja mensajes en la cola y la base de datos queda sin registros.

Si RabbitMQ falla despues del commit, el dato ya esta persistido y el error del listener se registra sin revertir la base de datos (comportamiento best-effort de mensajeria post-commit). Es una limitacion conocida del patron dual-write.

5. Consumo, reintentos y DLQ

Configuracion

Requeue al agotardefault-requeue-rejected = false
RecuperadorRejectAndDontRequeueRecoverer
Concurrenciaconcurrency = 1, max-concurrency = 3

Comportamiento

  • ACK automatico: el mensaje se confirma solo si el listener termina sin excepcion.
  • Reintentos: ante una excepcion, el mensaje se reintenta hasta 3 veces con backoff exponencial.
  • DLQ: al agotar los reintentos, el mensaje se rechaza sin requeue y se enruta al DLX, quedando en la DLQ con header x-death.
  • Sin bucle infinito: default-requeue-rejected=false evita el requeue perpetuo de mensajes envenenados.
  • DLQ sin consumidor: las colas de fallos retienen los mensajes para inspeccion manual en lugar de descartarlos.
Los consumidores son observacionales y sin side effects: validan (eventId, eventType, entidadId), registran en log y lanzan IllegalArgumentException ante un payload invalido. No acceden a repositorios, no mutan entidades ni stock, no llaman REST y no publican.

13. Limitaciones y trabajo futuro

  • Dual-write: un commit exitoso con RabbitMQ caido deja el dato persistido sin evento publicado. Limitacion arquitectonica conocida.
  • Idempotencia: no persistente. No necesaria mientras los consumidores sean observacionales; obligatoria antes de permitir mutaciones desde consumidores.
  • Replay de DLQ: inexistente. Las DLQ retienen mensajes para inspeccion manual.
  • Datasource local: las pruebas usan H2 y AWS usa PostgreSQL; no se agrega PostgreSQL al Compose en esta fase.
  • correlationId: permanece null hasta que exista un request-id o tracing real.
  • occurredAt: serializado como arreglo JSON; valido con contrato compartido, migrable a ISO-8601 en el futuro.

Fuera de alcance deliberadamente: manual ACK, Transactional Outbox, consumer de DLQ, replay automatico, Kafka, SAGA, CDC/Debezium y endpoints nuevos.
